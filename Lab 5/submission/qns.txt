Q1. Observe the stack segment information for testcase#2 and reason about it.
Ans.
	Output:
code: [0x100000000 - 0x13FFFFFFF] next_free: 0x100008000 perm: R_X
rodata: [0x140000000 - 0x17FFFFFFF] next_free: 0x140000000 perm: R__
data: [0x180000000 - 0x1801FFFFF] next_free: 0x180001000 perm: RW_
stack: [0x7FF000000 - 0x800000000] next_free: 0x7FFFFF000 perm: RW_
After expanding RW data and stack
code: [0x100000000 - 0x13FFFFFFF] next_free: 0x100008000 perm: R_X
rodata: [0x140000000 - 0x17FFFFFFF] next_free: 0x140000000 perm: R__
data: [0x180000000 - 0x1801FFFFF] next_free: 0x180001000 perm: RW_
stack: [0x7FF000000 - 0x800000000] next_free: 0x7FFFFD000 perm: RW_

	We can observe that the stack expands by 2 pages(the next_free decrease from 0x7FFFFF000 to 0x7FFFFD000). This happens because, when we dereference an address in the stack that has not yet 
	been allocated in the memory, then the OS will automatically expand the stack to prevent a seg fault from occuring. (Note: we verified that this is not caused by the expand() call by commenting 
	that line and running the program. Also, without the dereferencing statement, the stack expands by only 1 page, perhaps for the print statement and such.)


Part 4
------
Q1. Why is the number of VM areas less than the number of mmap calls for testcase#4? 
Ans. 
	If two or more mmap calls allocate areas that are both contiguous and have the same permissions, then they can be merged into a single virtual memory. Since all 4 mmap calls in testcase 4 have 
	the same read/write permissions, they can be merged into a single virtual memory area, thus the number of VM areas is only 1 evne though there are 4 mmap calls.


Q2. Why it is not so for testcase #3.
Ans.
	In testcase 3, there are no 2 contiguous mmap calls that have the same permissions meaning not 2 mmap calls can be merged, thus 4 different VM areas are created, one for each mmap call. Thus,
	number of VM areas in testcase 3 is 4 (and 3 after the munmap call).
